# MySQL design: schema, indexes, queries, migrations

Use this when writing or reviewing a MySQL (InnoDB) schema, an index, a query, or a migration. To measure a live database first, use [analyze-db-mysql.md](analyze-db-mysql.md). For HA commands, use [databases.md](databases.md).

Validate on realistic data with `EXPLAIN FORMAT=TREE` or `EXPLAIN ANALYZE` (MySQL 8.0.18+). `EXPLAIN ANALYZE` executes the query.

## Schema and data types

- **Engine and charset**: InnoDB with `utf8mb4` (`utf8mb3`/`utf8` cannot store all Unicode, including emoji).
- **Every table needs an explicit primary key.** InnoDB stores rows in primary key order (the clustered index), and every secondary index stores the primary key as its row pointer. A table without one gets a hidden key you cannot use. Group Replication, which Railway's MySQL HA uses, requires a primary key (or equivalent) on every replicated table.
- **Primary key shape**: default to `BIGINT UNSIGNED AUTO_INCREMENT`. Small, monotonically increasing keys append to the end of the clustered index and keep secondary indexes compact.
- **UUID keys**: random UUIDs as `CHAR(36)` cost 36 bytes in every secondary index and cause page splits on insert. If UUIDs are required, store `BINARY(16)` and prefer time-ordered values (UUIDv7 generated by the application, or `UUID_TO_BIN(UUID(), 1)` to reorder MySQL's time-based v1).
- **Integers**: pick the smallest type that fits the domain, but default to `BIGINT` for IDs and counters that grow.
- **Money**: `DECIMAL(p, s)` or integer minor units. Never `FLOAT`/`DOUBLE`.
- **Time**: `DATETIME` has a range to year 9999; `TIMESTAMP` converts through the session time zone and ends in 2038. Store UTC either way.
- **JSON**: the `JSON` type validates and stores a binary form. Index fields you filter on through a generated column or a functional index (8.0.13+). Promote frequently queried fields to real columns.
- **Strings**: `VARCHAR(n)` with a realistic limit. Large `TEXT`/`BLOB` columns in hot tables slow scans and sorts; split them into a side table when they are rarely read.
- **Strict mode**: keep `STRICT_TRANS_TABLES` (the default) so invalid data is rejected instead of truncated.

## Indexing

- **Composite order**: equality columns first, then the range or sort column. `(account_id, status, created_at)` serves `WHERE account_id = ? AND status = ? ORDER BY created_at`. A range condition on a column stops later columns from being used for further filtering.
- **Leftmost prefix**: `(a, b, c)` serves `a`, `a, b`, `a, b, c`. It does not serve `b` alone.
- **Covering**: when every selected and filtered column is in the index, `EXPLAIN` shows `Using index` and InnoDB never reads the row. The primary key is implicitly part of every secondary index, so do not append it.
- **Functional indexes** (8.0.13+): `CREATE INDEX idx_email_lower ON users ((LOWER(email)))` serves `WHERE LOWER(email) = ?`. MySQL has no partial (filtered) indexes; use a generated column plus an index, or a composite index that leads with the filter column.
- **Prefix indexes** on long strings (`col(32)`) save space but cannot cover a query or serve `ORDER BY` on the full value.
- **Full-text**: `FULLTEXT` indexes with `MATCH ... AGAINST` instead of `LIKE '%term%'`, which cannot use a B-tree index.
- **Cost**: every secondary index is updated on each write and competes for buffer pool memory.

### Audit unused and duplicate indexes

```sql
-- Indexes with no reads since the server started (requires performance_schema)
SELECT * FROM sys.schema_unused_indexes WHERE object_schema = DATABASE();

-- Indexes made redundant by another index
SELECT table_name, redundant_index_name, dominant_index_name, sql_drop_index
FROM sys.schema_redundant_indexes WHERE table_schema = DATABASE();
```

Counters reset on restart, and each HA member counts only its own reads. Before dropping, make the index invisible (`ALTER TABLE t ALTER INDEX idx INVISIBLE`), watch for regressions, then drop it. Making it visible again is instant.

## Query patterns

- **N+1**: replace per-row queries with a join or `WHERE id IN (...)` in batches, or the ORM's eager loading. In `performance_schema.events_statements_summary_by_digest`, an N+1 shows up as one digest with a very high `COUNT_STAR`.
- **Pagination**: `LIMIT 20 OFFSET 100000` reads and discards 100,000 rows. Use keyset pagination: `WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT 20`, backed by an index on `(created_at, id)`.
- **Sargable predicates**: avoid wrapping indexed columns in functions (`WHERE DATE(created_at) = ?` becomes a range on `created_at`). Match literal types to column types: comparing a `VARCHAR` column to a number converts every row and skips the index.
- **`OR` across columns** often prevents a single index from serving the query; rewrite as `UNION ALL` of indexed queries when it matters.
- **Batching**: multi-row `INSERT ... VALUES (...), (...)`; for large `UPDATE`/`DELETE`, loop over primary key ranges with `LIMIT` and commit each batch so locks stay short and replicas keep up.
- **Sorting**: `Using filesort` on a large result is a signal that the index does not match the `ORDER BY`.

## Transactions and locking

- The default isolation is `REPEATABLE READ`. Locking reads (`SELECT ... FOR UPDATE`), `UPDATE`, and `DELETE` take next-key locks on every index record they scan, not only the rows they change. A write whose `WHERE` has no usable index locks far more than intended.
- Keep transactions short. A long-running transaction holds locks and prevents purge of old row versions (growing undo history).
- Deadlocks are resolved by rolling back one transaction; the application must retry it (error 1213). `SHOW ENGINE INNODB STATUS` shows the latest deadlock. Access rows in a consistent order to reduce them.
- Work queues: `SELECT ... FOR UPDATE SKIP LOCKED` (8.0+) lets workers claim rows without blocking each other.

## Safe migrations

DDL needs an exclusive metadata lock at its start and end. If a long transaction or query is open on the table, the DDL waits, and every later query on that table queues behind the waiting DDL. Guard migrations:

```sql
SET SESSION lock_wait_timeout = 5;   -- seconds; fail fast and retry instead of stalling traffic
```

- **State the algorithm** so MySQL errors instead of silently copying the table: `ALTER TABLE t ADD COLUMN c INT, ALGORITHM=INSTANT;` or `ALGORITHM=INPLACE, LOCK=NONE`.
- **`INSTANT`** (8.0.12+): adding a column (any position from 8.0.29), dropping a column (8.0.29+), and some default and metadata changes complete without rebuilding the table.
- **`INPLACE, LOCK=NONE`**: secondary index creation and many other changes run online, but still rebuild or scan the table and add replication lag on large tables.
- **Copy operations** (changing a column type, the primary key, or the charset) rebuild the whole table. On large tables, use an online schema change tool (such as gh-ost or pt-online-schema-change) after checking it supports the topology, or use expand and contract: add a new column, dual-write, backfill in batches, switch reads, drop the old one later.
- Large transactions, including big backfills, can exceed Group Replication's transaction size limit on HA clusters; batch them.

## On Railway

- **Connect**: `railway connect <service>` opens the `mysql` client; `--tunnel-only` holds a tunnel for GUI tools.
- **Connections**: there is no managed pooler for MySQL. Size application pools so that `pool size x app replicas` stays below `max_connections`.
- **High availability**: Railway's MySQL HA is a Group Replication cluster behind HAProxy; all connections, reads included, go to the primary, and replicas exist for failover rather than read scaling. Applications must reconnect and retry after a failover. Every table needs a primary key before converting. Docs: [MySQL High Availability](https://docs.railway.com/databases/mysql-ha).
- **Recovery**: MySQL supports point-in-time recovery from archived binlogs and volume backups. Take a backup before risky migrations. Docs: [Point-in-Time Recovery](https://docs.railway.com/volumes/point-in-time-recovery), [Backups](https://docs.railway.com/volumes/backups).
